SDLC: Система обліку зустрічей для ІТ-компаній (MeetFlow)
Ідея продукту
«MeetFlow» — вебзастосунок на чистій Java 21 із використанням сервлетів та JSP-сторінок, розгорнутий на сервері додатків Apache Tomcat. Сервіс дозволяє користувачам керувати робочим розкладом, публікувати вільні слоти та бронювати зустрічі через зручний веб-інтерфейс. Усі дані надійно зберігаються в реляційній базі даних PostgreSQL, а бібліотека Lombok спрощує роботу з моделями даних.

Цільова аудиторія: розробники, тімліди та студенти, які вивчають класичну веб-розробку на Java без використання важких фреймворків на кшталт Spring.
Біль, який розв'язуємо: ручне ведення розкладу в блокнотах чи месенджерах створює плутанину, а вебзастосунок дає єдину точку для організації всіх внутрішніх зустрічей компанії.

Обрана методологія
Методологія: Kanban
Чому саме вона для цього продукту:
Оскільки проєкт розробляється самостійно або в невеликій команді, Kanban ідеально підходить для безперервного потоку задач (налагодження бази даних у PostgreSQL, написання сервлетів, верстка JSP-сторінок). Ми можемо бачити задачі на дошці та поступово реалізовувати функціонал у міру його готовності.

Чому не інші:

Waterfall: занадто жорстка методологія для навчального проєкту, де структура вебсторінок і SQL-запитів часто коригується в процесі розробки.

Scrum: вимагає регулярних і тривалих мітингів (спринти, демо, ретроспективи), які є надлишковими для розробки компактного вебзастосунку.

Фази життєвого циклу

3.1. Requirements (Вимоги)
Вхідні артефакти: Ідея продукту; вимоги до веб-інтерфейсу та баз даних.

Дії: Аналіз потреб; формування списку user stories; пріоритезація за MoSCoW.

Вихідні артефакти: Розділи 1–3 SDD; беклог задач.

Критерії виходу: Усі базові Must-історії та вимоги до сторінок зафіксовані.

3.2. Design (Проєктування)
Вхідні артефакти: Затверджені вимоги.

Дії: Проєктування реляційної моделі БД для PostgreSQL; проєктування структури сервлетів, DAO-класів та JSP-сторінок; побудова діаграм.

Вихідні артефакти: Повний SDD (архітектура, ER-модель, сценарії, структура URL).

Критерії виходу: Архітектура вебзастосунку повністю розписана в документації перед кодуванням.

3.3. Implementation (Розробка)
Вхідні артефакти: SDD; схема бази даних.

Дії: Написання бізнес-логіки та сервлетів на Java 21; використання Lombok для скорочення коду моделей; верстка JSP-сторінок; налаштування підключення до PostgreSQL через JDBC.

Вихідні артефакти: Робочий код у репозиторії; збірка у .war файл.

Критерії виходу: Усі функції реалізовані, проєкт збирається через Maven і готується до деплою на Tomcat.

3.4. Testing (Тестування)
Вхідні артефакти: Зібраний вебзастосунок.

Дії: Написання юніт-тестів за допомогою JUnit 5 та Mockito для сервісного рівня; ручне тестування HTTP-запитів, взаємодії з PostgreSQL та коректності відображення JSP-сторінок.

Вихідні артефакти: Зелені тести; звіт про перевірку.

Критерії виходу: Тести проходять успішно, інтерфейс коректно опрацьовує дії користувача.

3.5. Deployment (Розгортання)
Вхідні артефакти: .war файл застосунку; запущені локально PostgreSQL та Apache Tomcat.

Дії: Деплой .war файлу в директорію webapps сервера Apache Tomcat; перевірка підключення до бази даних.

Вихідні артефакти: Працюючий вебзастосунок на локальному сервері.

Критерії виходу: Сервер Tomcat успішно запускає застосунок, сторінки відкриваються в браузері.

3.6. Maintenance (Підтримка)
Вхідні артефакти: Працюючий вебсервер і база даних.

Дії: Виправлення дефектів, оптимізація SQL-запитів, оновлення інтерфейсу JSP.

Вихідні артефакти: Оновлені версії застосунку.

Критерії виходу: Стабільна робота сервісу без збоїв.

Definition of Done для продукту

Усі обов'язкові (Must-have) user stories реалізовані на Java 21 з використанням сервлетів, JSP та Lombok.

Дані успішно зберігаються та читаються з бази даних PostgreSQL.

Написані юніт-тести з використанням JUnit 5 та Mockito.

Застосунок успішно збирається Maven та працює під управлінням Apache Tomcat.

Документація (SDLC.md та SDD.md) повністю відповідає реалізованому коду.
